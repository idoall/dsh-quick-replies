### 版本对应

| 插件版本 | 已验证的 DeepSeek Harness | npm 发布状态 |
| --- | --- | --- |
| **`0.1.6`** | **`0.1.7-rc.2`（最新 RC）**、`0.1.7-rc.1`、`0.1.7-alpha.2` | 本次发布（`latest`） |
| `0.1.5` | `0.1.7-rc.1`、`0.1.7-alpha.2` | 已发布 |
| `0.1.4` | `0.1.7-alpha.2` | 已发布 |
| `0.1.3` | `0.1.5-rc.1` | 已发布 |
| `0.1.2` | `0.1.5-rc.1` | 已发布 |

### 为什么发这个版本

官方发布了 `0.1.7-rc.2`，这是 `0.1.7` 线上的第二个候选版本。本版的作用是**确认并声明对新 RC 的支持**：`0.1.7` 线的破坏性变更 `0.1.4` 已经吸收，rc.2 相对 rc.1 也没有动到本插件使用的任何接口，所以这次**代码零改动**，只有兼容性核对与文档更新。三处结论都来自实际产物与真实运行环境，不是推测：

1. **逐包比对了 rc.1 与 rc.2 的 npm 产物**（本插件 `dsh.client.inject` 声明的六个包）：`@deepseek-ai/dsh-settings` 的 `lib` 未变（仍无运行时 `register`，仍是 `describe` / `update` / `replace` / `mutate`）；`@deepseek-ai/dsh-client-ui-settings` 的 `lib/client.js` 未变（`ctx.configForms` 仍在，`ctx.settingsScope` 仍不存在）；`@deepseek-ai/dsh-api-settings-controller` 除 `package.json` / README 外逐字节相同（`settings.describe` / `settings.mutate` 未变）；`@deepseek-ai/dsh-client-connection` 的 `lib` 未变；`@deepseek-ai/dsh-api-remotes` 只有增量（新增 `schedule` 等 Remote 与凭据事件，局域网兜底依赖的 `settings/document-updated` 仍在事件表里）；`@deepseek-ai/dsh-api-session-controller` 的 `prompt` / `steer` / `queue` 面未变（仅新增 `initializeDefaultModel`）。
2. **在 rc.2 上实跑了宿主半。** 用 rc.2 的 CLI 对装有 `dsh-quick-replies` 0.1.5 的本 profile 做 schema 转储，条目 `/195 id=dsh-quick-replies` 报告 **`status: "schema"`**，其 `config` 正是本插件的 `Config`（volatile `schemaVersion` + 四个内置默认 `items`）。也就是说「宿主半 import → `Config` schema 注册 → 设置表单被识别」这条链在 rc.2 上成立。（转储里另有两条 `unrecognized Loader tree carrier` 警告，来自 DSH 自带的 `@deepseek-ai/dsh-agent-preset` 条目 `/178`、`/179`，与本插件无关。）
3. **在运行中的 rc.2 页面上确认客户端半边已加载**：页面中已注入本插件的 `data-plugin-css` 样式表，说明客户端 bundle 在 rc.2 上正常装载。（rc.2 的 `conversation.input.dock` 插槽是 `scope: "session"`，快捷栏只在会话输入区渲染，因此本次没有在浏览器里做点击发送的实测——发送路径的回归由仓库自带的 98 项测试覆盖。）

### 改了什么

- **声明记录新 RC。** `dsh.compatibility.dshReleases` 现同时记录 `0.1.7-rc.2`、`0.1.7-rc.1` 与 `0.1.7-alpha.2`。
- **peer 范围刻意保持不变。** `dsh.engines.dsh` 与 `peerDependencies['@deepseek-ai/dsh-settings']` 仍是 `>=0.1.7-alpha.2 <0.2.0`：按 node-semver 默认的预发布规则，只要范围里有比较符写了同一个 `major.minor.patch`，该版本的预发布就会被接纳，所以这个范围**同时覆盖** alpha.2、rc.1 与 rc.2。无需为 RC 放宽范围，也就不会顺带接纳未经测试的版本。
- **代码与存储模型完全不变。** `0.1.6` 与 `0.1.5` 的 `lib/` 产物一致，存储仍是 profile patch 中 `dsh-quick-replies` 条目的 `config`。`devDependencies` 里钉住的 `@deepseek-ai/dsh-settings` 也保持 `0.1.7-alpha.2`：它的 `lib/`（含 `lib/types`）在 alpha.2、rc.1、rc.2 三者之间逐字节相同，所以本仓库的类型检查等价于针对 rc.2 的类型检查。
- **文档。** 中英文 README 在顶部与兼容性章节更新支持版本；顺带修正 README 中「配置了 `NPM_TOKEN` 才发布 npm」的过时说法——实际是 OIDC 可信发布。

### rc.2 唯一的可见改动：设计令牌

rc.2 在客户端做了一次设计令牌改造：`@deepseek-ai/dsh-client-ui-theme` 定义 `--dsw-radius-*`（`xs/sm/md/lg/xl/panel`）与 `--dsw-focus-ring-*`，宿主自己的 dock 面板圆角由字面 `12px` 改为 `var(--dsw-radius-lg)`（= 16px），焦点环也改走令牌。这**不影响**本插件：插槽、props 契约、发送路径、存储都不涉及。本插件的圆角是自持的 `12px`，因此与刷新后的宿主 dock 有约 4px 的观感差异；本版**刻意不跟随令牌**——同一个 `--dsw-radius-lg` 在 rc.1 上也是 16px，而 rc.1 的宿主 dock 是 12px，跟随令牌只会把这点差异从最新版挪到旧版，属于纯观感取舍。

### 谁受影响

- **正在使用 `0.1.7-rc.2` 的人**：直接升级即可，本版就是为这个版本发布的。
- **从 `0.1.5` 升级的人**：**回复库无需迁移、配置无需改动**，代码没有变化。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续用插件 `0.1.3`。** `0.1.6` 声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`，低于它的版本未经本轮验证。

### 兼容性与升级

```sh
dsh plugin --profile web add dsh-quick-replies@0.1.6
```

宿主半边只在 DSH 启动时加载，所以**升级后需要重启 `dsh web`**；客户端半边刷新页面即生效。

从 `0.1.5` 升级不需要任何数据操作。若你仍在 `0.1.3` 或更早版本上、且尚未迁移回复库，请先按 [`0.1.4` 的说明](v0.1.4.md)把 `~/.dsh/settings.yaml` 的 `quick-replies.items` 搬到 profile patch 的 `dsh-quick-replies.config.items`。

### 限制

- **快捷栏依赖 DSH 的 `conversation.input.dock` 插槽**：DSH 大改输入区结构后快捷栏可能不再显示；但发送路径只走会话公开的 `prompt`，**不会碰草稿、引用、图片或光标**。
- **圆角与宿主 dock 有约 4px 观感差异**（见上「设计令牌」），这是刻意保留的取舍，不影响功能。
- **回复库属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写回复库。
- **空白会话不发送**：尚无历史消息的新会话会拒绝发送，避免误点「继续」开出一个空会话。
- **发送时机不由本插件决定**：空闲时 `queue`、运行中 `steer`，实际边界由 DSH 决定；插件不 cancel、不 stop，也不会声称「已打断」。

| `0.1.5` | `0.1.7-rc.1`, `0.1.7-alpha.2` | published |

### Why this release exists

The harness published `0.1.7-rc.2`, the second release candidate on the
`0.1.7` line. This release **confirms and declares support for that RC**:
`0.1.4` already absorbed the `0.1.7` breaking changes, and rc.2 touched nothing
this plugin consumes, so there is **no code change here** — only a
compatibility check and documentation updates. All three findings come from the
shipped artifacts and a real running environment, not from inference:

1. **The rc.1 and rc.2 npm artifacts were compared package by package** (the
   six packages in this plugin's `dsh.client.inject`).
   `@deepseek-ai/dsh-settings` ships an unchanged `lib` (still no runtime
   `register`; still `describe` / `update` / `replace` / `mutate`).
   `@deepseek-ai/dsh-client-ui-settings` ships an unchanged `lib/client.js`
   (`ctx.configForms` is still there, `ctx.settingsScope` is still absent).
   `@deepseek-ai/dsh-api-settings-controller` is byte-identical apart from
   `package.json` / README (`settings.describe` / `settings.mutate` unchanged).
   `@deepseek-ai/dsh-client-connection` ships an unchanged `lib`.
   `@deepseek-ai/dsh-api-remotes` changed additively only (new remotes such as
   `schedule`, extra credential events; `settings/document-updated`, which the
   LAN fallback subscribes to, is still in the event table).
   `@deepseek-ai/dsh-api-session-controller`'s `prompt` / `steer` / `queue`
   surface is unchanged (only `initializeDefaultModel` was added).
2. **The Host half was actually exercised on rc.2.** Using the rc.2 CLI to dump
   the profile schema of this profile — which has `dsh-quick-replies` 0.1.5
   installed — entry `/195 id=dsh-quick-replies` reports
   **`status: "schema"`**, and its `config` is exactly this plugin's `Config`
   (volatile `schemaVersion` plus the four built-in default `items`). So
   "Host half imports → `Config` schema registers → settings form is
   recognized" holds on rc.2. (The dump also prints two
   `unrecognized Loader tree carrier` warnings for DSH's own
   `@deepseek-ai/dsh-agent-preset` entries `/178` and `/179`; they are
   unrelated to this plugin.)
3. **The Client half was confirmed loaded on the running rc.2 page**: the page
   already carries this plugin's injected `data-plugin-css` stylesheet, so the
   client bundle loads on rc.2. (rc.2's `conversation.input.dock` slot is
   `scope: "session"`, so the bar only renders inside a session composer; no
   click-to-send run was performed in the browser this time — the send path is
   covered by the repository's 98 tests.)

### What changed

- **The new RC is recorded.** `dsh.compatibility.dshReleases` now lists
  `0.1.7-rc.2`, `0.1.7-rc.1` and `0.1.7-alpha.2`.
- **The peer range deliberately stays put.** `dsh.engines.dsh` and
  `peerDependencies['@deepseek-ai/dsh-settings']` remain
  `>=0.1.7-alpha.2 <0.2.0`: under node-semver's default prerelease rule a
  prerelease is admitted when some comparator names the same
  `major.minor.patch`, so the range already **covers** alpha.2, rc.1 and rc.2.
  Widening it for the RC would also admit versions this plugin never tested.
- **Code and storage model are unchanged.** `0.1.6` and `0.1.5` build the same
  `lib/` output, and the library still lives as the `dsh-quick-replies` entry's
  `config` in the profile patch. The pinned `@deepseek-ai/dsh-settings`
  `devDependency` also stays at `0.1.7-alpha.2`: its `lib/` (including
  `lib/types`) is byte-identical across alpha.2, rc.1 and rc.2, so this
  repository's typecheck is equivalent to a typecheck against rc.2.
- **Documentation.** Both READMEs state the new RC support at the top and in the
  compatibility section, and the stale "npm publish when `NPM_TOKEN` is set"
  line is corrected to the actual OIDC trusted publishing.

### rc.2's one visible change: design tokens

rc.2 shipped a design-token pass in the client: `@deepseek-ai/dsh-client-ui-theme`
now defines `--dsw-radius-*` (`xs/sm/md/lg/xl/panel`) and `--dsw-focus-ring-*`,
and the host's own dock panels moved from a literal `12px` to
`var(--dsw-radius-lg)` (= 16px), with focus rings on tokens too. This does
**not** affect the plugin: the slot, the props contract, the send path and
storage are untouched. This plugin's own corners stay at `12px`, so they are
about 4px tighter than the refreshed host docks. This release **deliberately
does not follow the tokens**: the same `--dsw-radius-lg` is also 16px on rc.1,
where the host docks are 12px, so adopting it would only move that small
difference from the newest version to the older ones. It is a purely visual
trade-off.

### Who is affected

- **Anyone on `0.1.7-rc.2`**: upgrade directly; this release exists for that
  version.
- **Upgrading from `0.1.5`**: **no library migration and no config change**;
  the code is identical.
- **Anyone still on an older DSH, including `0.1.6-alpha.2`: stay on plugin
  `0.1.3`.** `0.1.6` declares its Host requirement as
  `>=0.1.7-alpha.2 <0.2.0` and is not verified below it.

### Compatibility and upgrade

```sh
dsh plugin --profile web add dsh-quick-replies@0.1.6
```

The Host half loads only at DSH boot, so **restart `dsh web`** after upgrading;
the browser half reloads on a page refresh.

Upgrading from `0.1.5` needs no data operation at all. If you are still on
`0.1.3` or earlier and have not migrated yet, follow
[the `0.1.4` notes](v0.1.4.md) to move `quick-replies.items` from
`~/.dsh/settings.yaml` into `dsh-quick-replies.config.items` in the profile
patch.

### Limitations

- **The bar depends on DSH's `conversation.input.dock` slot**: a large change to
  the composer area can stop the bar from appearing. Sending itself only uses
  the Session's public `prompt`, so it **never touches the draft, references,
  images or the caret**.
- **Corners are about 4px tighter than the host docks** (see "design tokens"
  above); this is a deliberate trade-off and does not affect function.
- **The library is per DSH instance**: two independent DSH servers do not share
  it.
- **No permission model**: anyone who can reach the profile's authenticated
  routes can read and write the library.
- **Blank sessions refuse to send**: a brand-new Session with no history is
  refused, so a resume chip cannot accidentally create an empty conversation.
- **Timing is DSH's decision**: `queue` while idle, `steer` while running, and
  the plugin never cancels, never stops, and never claims it interrupted
  anything.
