### 为什么发这个版本

官方于 2026-09-28 发布了 `0.2.0-rc.1`。这是 `0.2.0` 线上的第一个候选版本，也是第一个**在 profile 加载时强制执行 peer 范围门禁**的版本。本版的作用是**核对 0.2.0-rc.1 并显式声明支持**：本插件依赖的每个接口在 0.2.0-rc.1 上都没有不兼容变更，所以**代码零改动**，改动只有版本声明与文档。所有结论都来自 0.2.0-rc.1 的实际产物、源码与真实运行环境，不是推测：

1. **在 0.2.0-rc.1 源码里逐项核对了消费契约**（`/Volumes/.../deepseek-harness` 对应 `dsh-v0.2.0-rc.1`）：
   - `conversation.input.dock` 插槽未变：仍是 `kind: "list"`、`scope: "session"`、owner `InputZone`（`packages/client/ui-conversation/src/client/contract/slots.ts`）；
   - 客户端静态模块表未变：`packages/client/web/src/seed.ts` 的 9 个模块（react、react/jsx-runtime、react-dom、react-dom/client、cordis、client-store、ui-slots、ui-primitives、ui-dockkit）与本插件 `tsdown.config.ts` 的 `PLATFORM_MODULES` 一一对应；
   - `window.__ModuleLoader__` 注册协议未变（`packages/client/modules/src/index.ts` 仍安装同一 facade，`dsh.client.inject` 仍由 roster 读取）；
   - `ctx.configForms` 仍是官方设置通道（`ui-settings` 系列包仍在 `ctx.configForms.get(...)`）；`ctx.settingsScope` 仍不存在；
   - `settings/document-updated` 事件仍在 settings 包的事件表里（局域网兜底不受影响）；
   - 会话 `prompt(content, mode, signal, requestId)` 签名未变（`ui-conversation` 的 `service.ts` 仍以相同参数调用）。
2. **类型检查直接针对 0.2.0-rc.1 通过**：`devDependencies` 里钉住的 `@deepseek-ai/dsh-settings` 升到 `0.2.0-rc.1`，`volatile` 字段、`SettingsProvider.configure`、`SettingsNamespace` 的类型契约全部未变。98 项测试（typecheck + vitest 全部项目，含按 harness 方式装载 `lib/index.js` 与 `lib/client.js` 的产物 lane）全部通过。
3. **在 0.2.0-rc.1 运行环境实测了 profile 门禁**：`dsh --profile web --dump-config`（CLI 0.2.0-rc.1）中 `dsh-quick-replies` 0.1.6 条目正常装载、无 skipping 警告，且条目 `config` 完整呈现（volatile `schemaVersion` + 内置默认 items）——「宿主半 import → `Config` schema 注册 → 设置值被识别」这条链在 0.2.0-rc.1 上成立。同一次转储里被门禁跳过的是三个第三方 bundle（dshmarket、@nanmicoder/dsh-agent-teams、dsh-code-index，它们的 peer 范围不含 0.2.x），与本插件无关。

### 0.2.0-rc.1 对插件作者改了什么

唯一的插件可见变化是**门禁**：`packages/boot/app-boot/src/plugin-compatibility.ts` 会在 profile 加载时检查每个 bundle 的 `@deepseek-ai/dsh-*` peer 依赖，用 `semver.satisfies(runtime, range, { includePrerelease: true })` 判定；不满足的 bundle 被跳过（stderr 打印 skipping 警告），除非用 `dsh plugin allow-version` 授予精确版本豁免。运行时 API 本身没有破坏性变更。

### 改了什么

- **peer 范围显式声明 0.2 线**。`dsh.engines.dsh` 与 `peerDependencies['@deepseek-ai/dsh-settings']` 从 `>=0.1.7-alpha.2 <0.2.0` 扩为 `>=0.1.7-alpha.2 <0.2.0-0 || 0.2.0-rc.1 || >=0.2.0 <0.3.0`。这里有个值得写清楚的细节：旧范围在 node-semver **默认**预发布规则下并不接纳 `0.2.0-rc.1`（没有任何比较符写 `0.2.0` 元组），此前 DSH 门禁放行它只是因为门禁用了 `includePrerelease: true`——换 npm 自身的 peer 检查就会报不匹配。新范围把意图写明：显式接纳已验证的 `0.2.0-rc.1` 与将来的 `0.2.x` 正式版，上界用 `-0` 挡住未经验证的 `0.2.0-rc.2` 等预发布。`0.1.7` 线的接纳行为与之前逐版本一致（已用 semver 对 8 个边界版本逐一验证）。
- **`dsh.compatibility.dshReleases` 记录 `0.2.0-rc.1`**，保留原有三条 `0.1.7` 线记录。
- **`devDependencies` 的 `@deepseek-ai/dsh-settings` 钉到 `0.2.0-rc.1`**：类型检查从「等价于 rc.2」升级为「直接针对 0.2.0-rc.1」。
- **文档。** 中英文 README 顶部与兼容性章节更新支持版本；本发布说明。
- **代码与存储模型完全不变。** 与 `0.1.6` 相同的源码，存储仍是 profile patch 中 `dsh-quick-replies` 条目的 `config`。

### 谁受影响

- **正在使用（或准备升级到）DSH `0.2.0-rc.1` 的人**：直接用 `0.1.7` 即可。
- **从 `0.1.6` / `0.1.5` 升级的人**：**回复库无需迁移、配置无需改动**，代码没有变化。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续用插件 `0.1.3`**；`0.1.3` 支持到 `0.1.5-rc.1`，`0.1.4`+ 支持 `0.1.7-alpha.2` 起的版本。
- **使用 dshmarket / dsh-agent-teams / dsh-code-index 的人**：这三个第三方 bundle 会被 0.2.0-rc.1 的门禁跳过；是否用 `dsh plugin allow-version` 豁免由你自己决定，与本插件无关。

### 兼容性与升级

```sh
dsh plugin --profile web add dsh-quick-replies@0.1.7
```

宿主半边只在 DSH 启动时加载，所以**升级后需要重启 `dsh web`**；客户端半边刷新页面即生效。

从 `0.1.6` / `0.1.5` 升级不需要任何数据操作。

### 限制

- **快捷栏依赖 DSH 的 `conversation.input.dock` 插槽**：DSH 大改输入区结构后快捷栏可能不再显示；但发送路径只走会话公开的 `prompt`，**不会碰草稿、引用、图片或光标**。
- **回复库属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写回复库。
- **空白会话不发送**：尚无历史消息的新会话会拒绝发送，避免误点「继续」开出一个空会话。
- **发送时机不由本插件决定**：空闲时 `queue`、运行中 `steer`，实际边界由 DSH 决定；插件不 cancel、不 stop，也不会声称「已打断」。
- **本版未在浏览器里做点击发送实测**（发送路径的回归由仓库自带的 98 项测试覆盖，客户端装载链路在 0.2.0-rc.1 上已按源码与产物核对）。

### Why this release exists

The harness published `0.2.0-rc.1` on 2026-09-28 — the first release candidate
on the `0.2.0` line and the first release that **enforces the peer-range gate
at profile load**. This release **checks that RC and explicitly declares
support for it**: every interface this plugin consumes is unchanged on
0.2.0-rc.1, so there is **no code change here** — only declaration and
documentation updates. Every finding below comes from the 0.2.0-rc.1
artifacts, source, and a real running environment, not from inference:

1. **Every consumed contract was verified against the 0.2.0-rc.1 source:**
   - The `conversation.input.dock` slot is unchanged (`kind: "list"`,
     `scope: "session"`, owner `InputZone`;
     `packages/client/ui-conversation/src/client/contract/slots.ts`).
   - The client static module table is unchanged: the nine modules in
     `packages/client/web/src/seed.ts` match this plugin's `PLATFORM_MODULES`
     one for one.
   - The `window.__ModuleLoader__` registration protocol is unchanged (the
     same facade is installed by `packages/client/modules/src/index.ts`, and
     `dsh.client.inject` rows are still read by the roster).
   - `ctx.configForms` is still the official settings channel (the
     `ui-settings-*` packages still call `ctx.configForms.get(...)`), and
     `ctx.settingsScope` is still absent.
   - `settings/document-updated` is still in the settings package's event
     table, so the LAN fallback is unaffected.
   - The session `prompt(content, mode, signal, requestId)` signature is
     unchanged (`ui-conversation`'s `service.ts` still calls it identically).
2. **The typecheck now runs directly against 0.2.0-rc.1**: the pinned
   `@deepseek-ai/dsh-settings` `devDependency` was raised to `0.2.0-rc.1`, and
   the `volatile` field, `SettingsProvider.configure`, and `SettingsNamespace`
   type contracts are all unchanged. All 98 tests pass (typecheck plus every
   vitest project, including the artifact lane that loads `lib/index.js` and
   `lib/client.js` the way the harness does).
3. **The profile gate was exercised on a real 0.2.0-rc.1 runtime**:
   `dsh --profile web --dump-config` (0.2.0-rc.1 CLI) loads the
   `dsh-quick-replies` 0.1.6 entry with no skipping warning, and the entry's
   `config` renders in full (volatile `schemaVersion` plus the built-in default
   items) — so "Host half imports → `Config` schema registers → settings values
   are recognized" holds on 0.2.0-rc.1. The bundles the gate skipped in that
   same dump are three third-party ones (dshmarket,
   @nanmicoder/dsh-agent-teams, dsh-code-index — their peer ranges exclude
   0.2.x), unrelated to this plugin.

### What 0.2.0-rc.1 changes for plugin authors

The one plugin-visible change is the **gate**:
`packages/boot/app-boot/src/plugin-compatibility.ts` now checks every bundle's
`@deepseek-ai/dsh-*` peer dependencies at profile load with
`semver.satisfies(runtime, range, { includePrerelease: true })`; a bundle that
fails is skipped (a skipping warning on stderr) unless an exact-version
exemption is granted with `dsh plugin allow-version`. There are no breaking
runtime API changes.

### What changed

- **The peer range explicitly declares the 0.2 line.** `dsh.engines.dsh` and
  `peerDependencies['@deepseek-ai/dsh-settings']` widen from
  `>=0.1.7-alpha.2 <0.2.0` to
  `>=0.1.7-alpha.2 <0.2.0-0 || 0.2.0-rc.1 || >=0.2.0 <0.3.0`. One detail worth
  writing down: under node-semver's **default** prerelease rule the old range
  did **not** admit `0.2.0-rc.1` (no comparator names the `0.2.0` tuple) — the
  DSH gate passed it only because it checks with `includePrerelease: true`, and
  npm's own peer check would have flagged the mismatch. The new range states
  the intent: explicitly admit the verified `0.2.0-rc.1` and future `0.2.x`
  stable releases, and use `-0` on the upper bound to keep unverified `0.2.0`
  prereleases (e.g. `0.2.0-rc.2`) out. Admission on the `0.1.7` line is
  version-for-version identical to before (verified against 8 boundary
  versions with semver).
- **`dsh.compatibility.dshReleases` records `0.2.0-rc.1`**, keeping the three
  existing `0.1.7`-line entries.
- **The pinned `@deepseek-ai/dsh-settings` `devDependency` moves to
  `0.2.0-rc.1`**: the typecheck upgrades from "equivalent to rc.2" to
  "directly against 0.2.0-rc.1".
- **Documentation.** Both READMEs state the new support at the top and in the
  compatibility section; this release note.
- **Code and the storage model are unchanged.** The source is identical to
  `0.1.6`, and the library still lives as the `dsh-quick-replies` entry's
  `config` in the profile patch.

### Who is affected

- **Anyone on (or moving to) DSH `0.2.0-rc.1`**: use `0.1.7`.
- **Upgrading from `0.1.6` / `0.1.5`**: **no data migration, no config
  change** — the code did not change.
- **Still on an older DSH (including `0.1.6-alpha.2`)**: stay on plugin
  `0.1.3` (verified up to `0.1.5-rc.1`); `0.1.4`+ covers `0.1.7-alpha.2` and
  later.
- **Users of dshmarket / dsh-agent-teams / dsh-code-index**: those third-party
  bundles are skipped by the 0.2.0-rc.1 gate; whether to grant
  `dsh plugin allow-version` exemptions is your call, unrelated to this plugin.

### Compatibility and upgrade

```sh
dsh plugin --profile web add dsh-quick-replies@0.1.7
```

The Host half loads only at DSH startup, so **restart `dsh web` after
upgrading**; the Client half takes effect on page refresh.

Upgrading from `0.1.6` / `0.1.5` needs no data operations.

### Limitations

- **The bar depends on DSH's `conversation.input.dock` slot**: if DSH
  restructures the input area, the bar may stop rendering; the send path only
  uses the session's public `prompt` and **never touches drafts, quotes,
  images, or the cursor**.
- **The library belongs to a single DSH instance**: two independent DSH
  services do not share it.
- **No permission model**: anyone who can reach the profile's authenticated
  routes can read and write the library.
- **Blank sessions refuse to send**: a brand-new session with no history
  refuses, so a stray click cannot open an empty conversation.
- **Send timing is not this plugin's decision**: `queue` while idle, `steer`
  while the top-level session runs — the actual boundary is DSH's; the plugin
  never cancels or stops, and never claims it interrupted anything.
- **No click-to-send run was performed in the browser this time** (the send
  path is covered by the repository's 98 tests; the client load chain was
  verified against the 0.2.0-rc.1 source and artifacts).
