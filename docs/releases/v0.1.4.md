<h3 id="cn-v0.1.4">插件 0.1.4 — 已验证 DeepSeek Harness 0.1.7-alpha.2</h3>

### 版本对应

| 插件版本 | 已验证的 DeepSeek Harness | npm 发布状态 |
| --- | --- | --- |
| **`0.1.4`** | `0.1.7-alpha.2` | 本次发布（`latest`） |
| `0.1.3` | `0.1.5-rc.1` | 已发布 |
| `0.1.2` | `0.1.5-rc.1` | 已发布 |
| `0.1.0`–`0.1.1` | `0.1.2-rc.1` | 已发布 |

### 为什么必须适配

DSH `0.1.7-alpha.2` 移除了本插件赖以工作的两套 API，另外改了一处依赖解析规则。第 ① 处会让旧版插件在 0.1.7 上**功能全灭**（设置命名空间永远注册不上，快捷栏只剩「回复库不可用」）；第 ② 处会让官方设置通道永远打不开；第 ③、④ 处与 `dsh-session-colors` 踩过的是同一个坑。四处都从运行实例的源码与清单里核实过，不是猜测：

1. **`ctx.settings.register()` 被删除了。** 0.1.7 的设置服务不再接受运行时注册命名空间，改为投影每个 Loader 条目**自身 `Config`** 的 volatile 字段，而且**设置表单的命名空间就是条目 id**。旧版的 `sctx.settings.register('quick-replies', schema, { base, applies, validate })` 会抛 `register is not a function`，并被插件的容错 `try/catch` 吞掉——于是 `quick-replies` 命名空间永远不存在，快捷栏在 0.1.7 上必然全灭。
2. **`ctx.settingsScope` 客户端服务被删除了。** 官方继任者是 `ctx.configForms.get(entryId)`（`@deepseek-ai/dsh-client-ui-settings`），旧通道永远打不开。
3. **link 插件的依赖解析规则变了。** 0.1.7 起，只有 link 插件的 **peer** 依赖会从运行实例解析；普通 `dependencies` 只在插件自己的 `node_modules` 下查找。旧版的 `@deepseek-ai/schemastery` 是普通依赖，而本仓库并不带 `node_modules`，于是 `link:` 装入后宿主半边 import 失败，**整个插件加载不起来**。
4. **peer 范围没有覆盖这个版本。** 旧版写的是 `>=0.1.5-rc.1`。按 node-semver 的默认规则，带预发布的版本只有在某个比较符写了**同一个 `major.minor.patch`** 时才被纳入，所以 `0.1.7-alpha.2` **不满足**这个范围，pnpm 会把它报成 unmet peer。（插件市场的发现流程传了 `includePrerelease`，所以它显示的是「未知」而不是「不兼容」——声明仍然不该这么写。）

### 改了什么

- **回复库成为插件自己的 `Config`。** 宿主半不再注册命名空间，改为导出 schemastery `Config`（`schemaVersion` 与 `items` 都标 `.volatile()`）。因此库的每次编辑都提交进运行中的引用并发 `loader/volatile-update`，**不会重挂载插件**——否则每保存一次快捷栏都会重启一次。
- **四个内置回复成为 schema 默认值**，也就是新 profile 解析出的 composition base；用户删光条目写入 `items: []` 仍是用户层覆盖，不会退回内置。
- **命名空间改为 `dsh-quick-replies`**，即 `cordis.patch.yml` 里 insert 的条目 id。**存储位置随之改变**：回复库不再写在 `~/.dsh/settings.yaml`，而是作为该条目的 `config` 落在当前 profile 的 `cordis.patch.yml`（`configEditor.edit()` 会为 bundle insert 出来的条目追加 profile override，写入仍是原子替换并保留 YAML 注释）。
- **抑制重复的自动表单页。** `Config` 出现后 DSH 会默认为该条目生成一个通用表单，与插件自带的管理弹窗重复；按官方惯例（`ui-theme`、`ui-chat`、`ui-conversation` 同样做法）注册 `settings.configure({ auto: false })`。命名空间行本身仍留在 `settings.describe()` 里，读写不受影响。
- **客户端官方通道改为 `ctx.configForms.get(entryId)`**，新增 `configFormScope.ts` 把它投影到插件自己的 scope 契约；`mutate` 返回 `false`（被拒）会翻译成拒绝，管理界面的冲突提示得以保留。
- **局域网兜底不变。** 非回环页面上官方表单被固定为 `memory` 且永远 `unavailable`，插件仍回落到同一个公开 Remote（`settings.describe` / `settings.mutate`）直连 Host，多设备共享语义与 revision 栅栏保持不变。
- **`@deepseek-ai/schemastery` 改为 peer。** 从 `dependencies` 移到 `peerDependencies`（保留 `devDependencies` 供本仓库自测），0.1.7 会把它解析到运行实例自带的版本。
- **声明与发布版本对齐。** `@deepseek-ai/dsh-settings` 的 peer 范围与 `dsh.engines.dsh` 都写 `>=0.1.7-alpha.2 <0.2.0`，`dsh.compatibility.dshReleases` 记为 `0.1.7-alpha.2`，并补 `dsh.manifestVersion`、`dsh.client.inject` 加 `@deepseek-ai/dsh-api-remotes`。

### 谁受影响

- **在 DSH `0.1.7-alpha.2` 上使用本插件的人**：现在能正常装入、读取与保存。
- **从 `0.1.3` 升级的人：回复库需要迁移一次。** 旧库存在 `~/.dsh/settings.yaml` 的 `quick-replies` 段；0.1.7 首次启动会把这个文件重命名为 `settings.yaml.imported`，而它的自动导入会因为找不到同名条目而**跳过这一段**。请把 `quick-replies.items` 里的条目搬到新位置（见下方「兼容性与升级」），否则快捷栏会回到四个内置默认值。
- **还在更旧 DSH（包括 `0.1.6-alpha.2`）的人：请继续用插件 `0.1.3`。** `0.1.4` 声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`，低于它的版本未经本轮验证。

### 兼容性与升级

```sh
dsh plugin --profile web add dsh-quick-replies@0.1.4
```

宿主半边只在 DSH 启动时加载，所以**升级后需要重启 `dsh web`**；客户端半边刷新页面即生效。

把旧库搬到新位置：在 profile 的 `cordis.patch.yml` 里给该条目一个 `config`（或者直接在插件自己的管理弹窗里重新录入一遍）：

```yaml
- id: dsh-quick-replies
  name: dsh-quick-replies
  config:
    items:
      - id: qr-default-continue
        label: 继续
        content: 继续
        enabled: true
```

`items` 一旦存在就整体替换内置默认值（数组是整体替换，不做合并），所以要把想保留的条目一次列全。

### 限制

- **快捷栏依赖 DSH 的 `conversation.input.dock` 插槽**：DSH 大改输入区结构后快捷栏可能不再显示；但发送路径只走会话公开的 `prompt`，**不会碰草稿、引用、图片或光标**。
- **回复库属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写回复库。
- **空白会话不发送**：尚无历史消息的新会话会拒绝发送，避免误点「继续」开出一个空会话。
- **发送时机不由本插件决定**：空闲时 `queue`、运行中 `steer`，实际边界由 DSH 决定；插件不 cancel、不 stop，也不会声称「已打断」。

### Why an adaptation was required

DSH `0.1.7-alpha.2` removed the two APIs this plugin was built on and changed one
dependency-resolution rule. The first left the old build functionally dead on
0.1.7 (its settings namespace could never register, so the bar could only say
"reply library unavailable"); the second closed the official settings channel
for good; the third and fourth are the same trap `dsh-session-colors` hit. All
four were checked against the running instance's own source and manifests, not
inferred:

1. **`ctx.settings.register()` is gone.** The 0.1.7 settings service no longer
   accepts a namespace registered at runtime: it projects the volatile fields of
   each Loader entry's **own `Config`**, and a form namespace **is the entry
   id**. The old `sctx.settings.register('quick-replies', schema, { base,
   applies, validate })` throws `register is not a function`, which the plugin's
   defensive `try/catch` swallowed — so the namespace never existed and the bar
   was bound to fail on 0.1.7.
2. **`ctx.settingsScope` is gone.** Its official successor is
   `ctx.configForms.get(entryId)` (`@deepseek-ai/dsh-client-ui-settings`); the
   old channel can never open.
3. **Linked-plugin dependency resolution changed.** From 0.1.7, only a linked
   plugin's **peer** dependencies resolve from the running installation; a plain
   `dependency` is looked up under the plugin's own `node_modules`, which a
   `link:` install does not populate. `@deepseek-ai/schemastery` was a plain
   dependency and this repository ships no `node_modules`, so after a `link:`
   install the Host half failed to import and **the plugin never loaded**.
4. **The peer range did not cover the release.** It read `>=0.1.5-rc.1`. Under
   node-semver's default rule a version that carries a prerelease is admitted
   only when some comparator names the same `major.minor.patch`, so
   `0.1.7-alpha.2` does **not** satisfy that range and pnpm reports it as an
   unmet peer. (The plugin market's discovery passes `includePrerelease`, so it
   showed "unknown" rather than "incompatible" — the declaration was still
   wrong.)

### What changed

- **The reply library is the plugin's own `Config`.** The Host half no longer
  registers a namespace; it exports a schemastery `Config` (`schemaVersion` and
  `items` both `.volatile()`). Every library edit therefore commits into the
  running references and emits `loader/volatile-update` — it does **not**
  remount the plugin, which would otherwise restart the bar on every save.
- **The four built-in replies are the schema default**, i.e. the composition
  base a fresh profile resolves to; deleting every chip stores `items: []`,
  which stays a user override and never falls back to the built-ins.
- **The namespace is now `dsh-quick-replies`**, the entry id inserted by
  `cordis.patch.yml`. **Storage moved with it**: the library no longer lives in
  `~/.dsh/settings.yaml` but as that entry's `config` in the active profile's
  `cordis.patch.yml` (`configEditor.edit()` appends the profile override for an
  inserted bundle row; the write is still an atomic replace that preserves YAML
  comments).
- **The duplicate auto-generated form is suppressed.** A `Config` makes DSH
  generate a generic settings form for the entry, which would sit beside the
  plugin's own management dialog; the documented
  `settings.configure({ auto: false })` is registered instead, as `ui-theme`,
  `ui-chat` and `ui-conversation` do. The namespace row stays in
  `settings.describe()` either way, so reads and writes are unaffected.
- **The client's official channel is `ctx.configForms.get(entryId)`**, projected
  onto the plugin's own scope contract by the new `configFormScope.ts`; a
  refused write (`mutate` answering `false`) becomes a rejection, so the
  management UI still surfaces a conflict.
- **The LAN fallback is unchanged.** On a non-loopback page the official form is
  pinned to `memory` and terminally `unavailable`, so the plugin still falls
  back to the same public Remote (`settings.describe` / `settings.mutate`) and
  keeps one shared Host library, with the revision fence intact.
- **`@deepseek-ai/schemastery` is a peer.** It moved from `dependencies` to
  `peerDependencies` (kept in `devDependencies` for this repository's own
  tests), so 0.1.7 resolves it from the running installation.
- **The declared ranges match the release.** The `@deepseek-ai/dsh-settings`
  peer range and `dsh.engines.dsh` both read `>=0.1.7-alpha.2 <0.2.0`,
  `dsh.compatibility.dshReleases` records `0.1.7-alpha.2`, `dsh.manifestVersion`
  was added, and `dsh.client.inject` gained `@deepseek-ai/dsh-api-remotes`.

### Who is affected

- **Anyone using this plugin on DSH `0.1.7-alpha.2`**: it now installs, reads
  and saves again.
- **Upgrading from `0.1.3`: the reply library needs a one-time migration.** The
  old library lived in the `quick-replies` section of `~/.dsh/settings.yaml`;
  the first 0.1.7 boot renames that file to `settings.yaml.imported`, and its
  automatic import **skips this section** because no entry carries that name.
  Move the entries from `quick-replies.items` to the new location (see below),
  or the bar falls back to the four built-in defaults.
- **Anyone still on an older DSH, including `0.1.6-alpha.2`: stay on plugin
  `0.1.3`.** `0.1.4` declares its Host requirement as
  `>=0.1.7-alpha.2 <0.2.0` and is not verified below it.

### Compatibility and upgrade

```sh
dsh plugin --profile web add dsh-quick-replies@0.1.4
```

The Host half loads only at DSH boot, so **restart `dsh web`** after upgrading;
the browser half reloads on a page refresh.

To move the old library: give the entry a `config` in the profile's
`cordis.patch.yml` (or simply re-enter the entries in the plugin's own
management dialog):

```yaml
- id: dsh-quick-replies
  name: dsh-quick-replies
  config:
    items:
      - id: qr-default-continue
        label: 继续
        content: 继续
        enabled: true
```

Once `items` exists it replaces the built-in defaults wholesale (arrays replace,
they do not merge), so list every entry you want to keep in one go.

### Limitations

- **The bar depends on DSH's `conversation.input.dock` slot**: a large change to
  the composer area can stop the bar from appearing. Sending itself only uses
  the Session's public `prompt`, so it **never touches the draft, references,
  images or the caret**.
- **The library is per DSH instance**: two independent DSH servers do not share
  it.
- **No permission model**: anyone who can reach the profile's authenticated
  routes can read and write the library.
- **Blank sessions refuse to send**: a brand-new Session with no history is
  refused, so a resume chip cannot accidentally create an empty conversation.
- **Timing is DSH's decision**: `queue` while idle, `steer` while running, and
  the plugin never cancels, never stops, and never claims it interrupted
  anything.
