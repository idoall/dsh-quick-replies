### 为什么发这个版本

`0.1.7` 的 peer 上界写成 `<0.2.0-0`，把未经验证的 `0.2.0-rc.2` 挡在门外——这是当时刻意的。DSH 升到 `0.2.0-rc.2` 后，这条件就变成了拒载：`0.2.0-rc.2` 既不等于 `0.2.0-rc.1`，也不小于 `0.2.0-0`，于是 `@deepseek-ai/dsh-settings` 这个 peer 判定为不满足，整个 bundle 被 profile 门禁跳过，快捷栏从界面上消失。

一个容易误判的地方：**当前 profile 里锁的是 `0.1.6`，它反而能装上**。因为 `0.1.6` 的范围是 `>=0.1.7-alpha.2 <0.2.0`，而门禁用 `semver.satisfies(..., { includePrerelease: true })` 比对——在这个规则下 `<0.2.0` **接纳** `0.2.0-rc.2`。也就是说 `0.1.6` 是靠门禁的宽松规则侥幸通过的，换成 node-semver 默认规则同样不接纳。所以坏掉的是 npm 上的 `latest`（`0.1.7`），而不是 profile 里那份旧的 `0.1.6`：任何人 `pnpm update` 或新装拿到 `0.1.7`，就会丢插件。

- **这个新范围的接纳表在两种判定规则下完全一致**（这是相对 `0.1.6` 与 `0.1.7` 的实质改进：`0.1.6` 只在宽松规则下接纳 `rc.2`，`0.1.7` 在两种规则下都不接纳 `rc.2`，声明与事实都对不上）：

  | DSH 版本 | node-semver 默认规则 | DSH 门禁（`includePrerelease: true`） |

### Why this release exists

`0.1.7`'s peer upper bound was `<0.2.0-0`, deliberately keeping the untested `0.2.0-rc.2` out. Once DSH moved to `0.2.0-rc.2` that same bound turned into a refusal: `0.2.0-rc.2` is neither equal to `0.2.0-rc.1` nor less than `0.2.0-0`, so the `@deepseek-ai/dsh-settings` peer counts as unsatisfied, the whole bundle is skipped by the profile gate, and the quick-reply bar disappears from the UI.

The easy misreading: **the profile here still pins `0.1.6`, and that one does load**. `0.1.6`'s range is `>=0.1.7-alpha.2 <0.2.0`, and the gate compares with `semver.satisfies(..., { includePrerelease: true })` — under that rule `<0.2.0` **does** admit `0.2.0-rc.2`. So `0.1.6` passes only by the gate's lenient rule; node-semver's default rule rejects it too. The broken artifact is npm's `latest` (`0.1.7`), not the older `0.1.6` sitting in the profile: anyone running `pnpm update` or installing fresh gets `0.1.7` and loses the plugin.

### ⚠️ Changes

- The peer and `dsh.engines.dsh` ranges become `>=0.1.7-alpha.2 <0.2.0-0 || 0.2.0-rc.1 || 0.2.0-rc.2 || >=0.2.0 <0.3.0`: the verified `0.1.7` line, `0.2.0-rc.1` and `0.2.0-rc.2` pinned exactly, and the stable `0.2.0` line up to `<0.3.0`.
- **The new range's admission table is identical under both rules** — the substantive improvement over `0.1.6` and `0.1.7` (`0.1.6` admits `rc.2` only under the lenient rule; `0.1.7` admits it under neither, so its declaration matched nothing):

  | DSH version | node-semver default rule | DSH gate (`includePrerelease: true`) |
  | --- | --- | --- |
  | `0.1.7-alpha.2` / `0.1.7-rc.1` / `0.1.7-rc.2` | ✅ | ✅ |
  | `0.2.0-rc.1` / `0.2.0-rc.2` | ✅ | ✅ |
  | `0.2.0-rc.3` and other unverified `0.2.0` prereleases | ❌ | ❌ |
  | `0.2.0` stable and `0.2.x` | ✅ | ✅ |
  | `0.3.0` | ❌ | ❌ |

  In other words `0.2.0-rc.3` onward will still need another adaptation release — that is this repo's standing "declare only what was verified" trade-off, not an oversight.
- `dsh.compatibility.dshReleases` records `0.2.0-rc.2`; the pinned `@deepseek-ai/dsh-settings` devDependency moves to `0.2.0-rc.2` (so this repo's typecheck now runs directly on the `0.2.0-rc.2` type surface); both READMEs updated. **Zero product-code change.**

### ✅ Verified

- **Item-by-item rc.1 → rc.2 source check: nothing this plugin consumes changed incompatibly.**
  - The `conversation.input.dock` slot contract directory (`packages/client/ui-conversation/src/client/contract/`) has **zero diff**.
  - The client static module table (`packages/client/web/src/seed.ts`, nine platform modules) has **zero diff** and still matches this plugin's `tsdown.config.ts` baseline one for one; the `window.__ModuleLoader__` registration protocol is unchanged.
  - `ctx.configForms` is still the official settings channel (`config-form.ts` in `ui-settings` is byte-identical across rc.1/rc.2; `settingsScope` is still gone).

  - The session `prompt(content, mode, signal, requestId)` call signature is unchanged (both call sites in `ui-conversation/src/client/service.ts` are identical).
  - `@deepseek-ai/dsh-client-*` / `dsh-api-*` show only version bumps and additions (`api/remotes` merely adds `userQuestionsRemote`); the settings packages change only their `package.json` version field.

- Typecheck runs directly against `0.2.0-rc.2`'s `@deepseek-ai/dsh-settings` and passes; **all 98 tests green** (including the artifact lane that loads `lib/` the way the harness does); `pnpm build` emits `lib/index.js`, `lib/index.d.ts`, `lib/client.js`.
